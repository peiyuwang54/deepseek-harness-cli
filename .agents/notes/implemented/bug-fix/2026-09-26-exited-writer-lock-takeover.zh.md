# Agent Note: 接管已退出写入方的锁

Status: implemented

[English](2026-09-26-exited-writer-lock-takeover.md) | 中文

## 问题

`withFileLock` 以独占创建方式生成 `<file>.lock`，并在 `finally` 中移除。进程若在清理前被终止，就会留下锁，之后的设置、凭据或托管 MCP catalog 写入都会超时，直到操作者手动删除。文件存续时间无法区分已崩溃的持有者与暂停但仍存活的写入方。

## 决策

锁沿用现有的 `<pid>\n` 记录。竞争者使用信号 0 探测该 PID，并且只在收到 `ESRCH` 后认定持有者不存在；存活进程、`EPERM`、竞争者自身的 PID，以及格式错误或不可读的记录都继续视为竞争。

针对同一个已退出持有者的竞争者通过以 `wx` 创建的 `<file>.lock.takeover-<record hash>` 串行化。认领者在移除锁前重新读取记录并再次探测 PID，随后移除认领文件并立即重试获取。因此，记录已经变化或 PID 已重新存活时都会保留锁。认领竞争和暂时无法移除的锁会回到有界退避；无关的认领创建失败仍会响亮失败。

可选的 `waitMs` 获取设置允许合理持锁时间更长的调用方延长默认两秒期限。它只改变等待存活或无法证明已退出的持有者的时长，不会削弱接管校验。

## 考虑过的替代方案

**移除超过固定时长的锁。** 不采用，因为时长无法区分已经崩溃的进程与暂停或缓慢运行的存活持有者。

**一次 PID 探测失败后立即移除锁。** 不采用，因为在探测与移除之间，另一名竞争者可能替换锁，操作系统也可能复用该 PID。认领文件、第二次读取记录和第二次探测会封闭这两种竞态。

**使用由内核释放的锁。** 暂缓，因为零依赖工具必须与通过锁文件协调的早期版本互操作；替换协议时需要在过渡期同时持有两种机制。

## 测试

聚焦覆盖通过注入的进程探测和文件系统故障固定以下行为：接管已退出持有者、在 POSIX 上恢复真实已退出进程的锁、8 名并发竞争者不重叠、存活和无效记录、其他用户和自身 PID 处理、记录替换、PID 复用、不可读锁、认领竞争、移除失败，以及无关失败响亮抛出。该包的语句、分支、函数和行覆盖率保持 100%。

## 后果

由已被证明不存在的进程留下的锁会在下次写入时恢复，无需操作者处理。格式错误的记录、被复用的 PID 或遗留认领仍需检查。PID 探测只作用于同一主机和 namespace，因此不同主机或不同 PID namespace 中的写入方不得共享这些锁文件。
