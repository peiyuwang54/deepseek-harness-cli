# Agent Note: CLI 分发保留失败状态并验证发布来源

Status: implemented

[English](2026-10-26-cli-distribution-hardening.md) | 中文

## 问题

npm shim 如果吞掉自己的终止信号，会把中断的任务报告为成功。先于平台依赖发布 shim 会导致安装不完整，把手动触发的版本输入插入 Shell 源码则允许命令注入。与可执行文件一起下载的校验和可以检测损坏，却无法识别产物的构建来源。

## 决策

[分发设计](../feature/2026-08-15-dsh-cli-exe-distribution.md) 保留三个通道。shim 在向自身重新发送子进程的终止信号前，移除自己的信号转发监听器，保留普通退出码，并在同步或异步 spawn 失败时报告错误而不打印 Node 堆栈。

发布工作流通过环境变量接收手动输入的版本，并在输出 job 参数前，将所有版本来源验证为 `X.Y.Z` 或 `X.Y.Z-rc.N`。五个平台版本全部先于主版本发布。重试跳过 registry 中已存在的版本并修复其 dist-tag；只有明确的 registry `E404` 才允许发布新版本。registry 认证和传输错误会终止发布。

CLI 发布工作流中的每个 Action 都固定到 commit。打包 job 为发布 tarball 签署 GitHub 来源证明，npm 发布则使用 job 级 OIDC 请求来源证明。在包所有者于 npm 配置 Trusted Publishing 前，npm 认证保留受保护的 `NPM_TOKEN`；修改仓库无法建立这一信任关系。

POSIX 安装器通过 fish 自己的 `conf.d` 文件配置 PATH；在 macOS Bash 下，同时配置首个已存在的登录配置文件与 `.bashrc`。没有登录配置文件时创建 `.bash_profile`。

## 曾考虑的替代方案

**转发信号后以零退出。** 这会向自动化隐藏取消状态。恢复默认信号处理可以保留操作系统的终止状态。

**先发布主包，或在重试时重新发布已有版本。** 前者会暴露缺失的依赖，后者因 npm 版本不可变而失败。先发布依赖并明确处理 registry 错误，可以支持中断后的重试。

**立即移除 `NPM_TOKEN`。** 所有者将此工作流注册为受信任发布者前，OIDC 认证会失败。保留 token 认证期间可以独立加入来源证明。

**把发布校验和当作来源证明。** 校验和与可执行文件可以同时被替换。签署的来源证明提供可单独验证的工作流身份；安装器的自动检查仍以校验和为基础。

## 后果

发布 job 需要限定范围的证明与 OIDC 权限。用户可以显式验证下载 tarball 的发布工作流身份；安装器不要求 GitHub CLI，也不自动强制执行此验证。registry 发布与证明签发需要实际发布才能验证。

## 验证

shim 测试覆盖普通退出、spawn 错误、信号转发和真实 POSIX 终止。工作流测试在 fake registry 下执行版本校验与发布脚本，覆盖恢复、发布失败和认证失败。安装器测试通过真实安装器和隔离的 home 目录验证 fish 与 macOS Bash 配置。这些检查不需要生产凭据。
