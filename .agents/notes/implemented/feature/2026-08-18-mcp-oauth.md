# Agent Note: Persistent MCP OAuth for the CLI

Status: implemented

English | [中文](2026-08-18-mcp-oauth.zh.md)

## Problem

Managed MCP servers supported stdio and Streamable HTTP transports, but an HTTP server that required OAuth had no first-class login flow. Putting bearer tokens in `mcp.json` would expose secrets to configuration projection and make refresh ownership unclear.

## Decision

`deepseek mcp auth <name>` owns an explicit OAuth 2.1 authorization-code flow for Streamable HTTP servers. The command uses the MCP SDK's discovery, dynamic registration, PKCE, refresh, and token exchange, opens the authorization URL when a desktop opener is available, and receives the callback on a loopback listener. `--no-open`, `--scope`, `--code`, and injectable browser/timeout options cover headless and test environments.

Registration metadata, discovery state, PKCE material, and tokens are stored atomically in a per-server file below the DSH home directory with private directory and file modes. The managed catalog stores only the state path and callback URL. Normal profile startup reuses the provider for token refresh and never opens a browser; malformed or mismatched state fails closed.

## Alternatives considered

**Store a bearer token in the MCP catalog.** Rejected: catalog projection and config dumps would create avoidable secret exposure, and refresh would be owned by every caller.

**Start OAuth automatically during profile boot.** Rejected: a non-interactive or headless profile must not bind a local listener or open a browser as a side effect of startup.

**Implement provider-specific OAuth in each MCP transport.** Rejected: the MCP SDK already owns protocol discovery and PKCE behavior; one file-backed provider keeps durable state and security policy in the harness.

## Consequences

HTTP MCP servers can be authorized once and then reconnect with persisted refresh state. Users in terminals without a browser can copy the printed URL and provide the returned code. The token file is machine-local and must be removed manually when credentials need revocation; the CLI does not claim to revoke credentials at the provider.

## Verification

Focused Vitest tests cover private state persistence, one-time PKCE cleanup, invalidation, malformed state, CLI catalog projection, manual-code exchange, stdio rejection, and the `/mcp auth` guidance. The MCP client and CLI TypeScript programs, host library build, documentation pairing, and repository documentation gates pass before publication.
