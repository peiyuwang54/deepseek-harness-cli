# Agent Note：CLI 持久化 MCP OAuth

状态：已实现

English | [中文](2026-08-18-mcp-oauth.md)

## 问题

托管 MCP server 已支持 stdio 和 Streamable HTTP，但需要 OAuth 的 HTTP server 没有首类登录流程。把 bearer token 放入 `mcp.json` 会让密钥进入配置投影，也无法明确刷新状态的所有权。

## 决策

`deepseek mcp auth <name>` 为 Streamable HTTP server 负责显式的 OAuth 2.1 authorization-code 流程。该命令使用 MCP SDK 的发现、动态注册、PKCE、刷新和 token 交换；桌面环境会打开授权 URL，并通过 loopback listener 接收回调。`--no-open`、`--scope`、`--code` 以及可注入的浏览器和超时选项覆盖无头与测试环境。

注册元数据、发现状态、PKCE 数据和 token 通过原子写入保存到 DSH home 下每个 server 独立的私有文件，目录与文件使用私有权限。托管 catalog 只保存状态路径和回调 URL。普通 profile 启动会复用 provider 刷新 token，但不会打开浏览器；损坏或不匹配的状态会直接失败。

每个启用 OAuth 的 Streamable HTTP 传输都会为完整 SDK 流程使用带校验的 fetch 实现。远端 MCP server 必须使用 HTTPS；本地回环 server 可使用 HTTP 开发流程。对确切 MCP 资源的请求仍由用户配置；发现、动态注册、token 交换、刷新和每个重定向步骤都会拒绝非 HTTP 协议、URL 凭据、不安全的远端 HTTP、从远端 server 访问的回环／私有／保留地址、包含此类地址的 DNS 结果，以及无法解析的主机。`resource_metadata` challenge 必须保持在已配置 MCP server 的源上。跨源重定向会在下一次请求前移除 authorization、cookie 和 proxy-authorization header。

## 备选方案

**把 bearer token 保存到 MCP catalog。** 否决：catalog 投影和配置转储会造成不必要的密钥暴露，也会让每个调用方分别负责刷新。

**在 profile 启动时自动开始 OAuth。** 否决：无头或非交互 profile 不应因启动副作用绑定本地 listener 或打开浏览器。

**在每个 MCP transport 中分别实现 OAuth。** 否决：MCP SDK 已负责协议发现和 PKCE；单一文件 provider 能让 Harness 统一持有持久状态和安全策略。

**依赖 MCP SDK 的默认 fetch。** 否决：协议校验不会决定此部署可以联系哪些网络目标。注入一个传输级 fetch，就能对发现、注册、token 交换、刷新和重定向统一应用快速失败的网络策略，而无需重复实现这些 OAuth 操作。

## 影响

HTTP MCP server 可以授权一次，之后用持久化的刷新状态重新连接。没有浏览器的终端可以复制打印出的 URL，并提供返回的 code。远端 OAuth 端点无法借助 Harness 访问私有网络；私有网络 OAuth 部署需要公开的 HTTPS 端点，回环开发流程仍然可用。每次非资源请求前都会解析非 IP 字面量的远端主机名，因此 OAuth 流量会增加解析器工作。token 文件保存在本机，需要撤销凭据时由用户手动删除；CLI 不声称代 provider 撤销凭据。

## 验证

针对性的 Vitest 覆盖私有状态持久化、一次性 PKCE 清理、失效处理、损坏状态、协议与地址拒绝、DNS 失败和私有结果、challenge 源、重定向复检和 secret 移除、CLI catalog 投影、手动 code 交换、拒绝 stdio 以及 `/mcp auth` 提示。发布前 MCP client 与 CLI TypeScript 程序、host library 构建、文档配对和仓库文档门禁均通过。
