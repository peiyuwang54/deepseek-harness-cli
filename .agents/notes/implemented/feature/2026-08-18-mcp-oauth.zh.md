# Agent Note：CLI 持久化 MCP OAuth

状态：已实现

English | [中文](2026-08-18-mcp-oauth.md)

## 问题

托管 MCP server 已支持 stdio 和 Streamable HTTP，但需要 OAuth 的 HTTP server 没有首类登录流程。把 bearer token 放入 `mcp.json` 会让密钥进入配置投影，也无法明确刷新状态的所有权。

## 决策

`deepseek mcp auth <name>` 为 Streamable HTTP server 负责显式的 OAuth 2.1 authorization-code 流程。该命令使用 MCP SDK 的发现、动态注册、PKCE、刷新和 token 交换；桌面环境会打开授权 URL，并通过 loopback listener 接收回调。`--no-open`、`--scope`、`--code` 以及可注入的浏览器和超时选项覆盖无头与测试环境。

注册元数据、发现状态、PKCE 数据和 token 通过原子写入保存到 DSH home 下每个 server 独立的私有文件，目录与文件使用私有权限。托管 catalog 只保存状态路径和回调 URL。普通 profile 启动会复用 provider 刷新 token，但不会打开浏览器；损坏或不匹配的状态会直接失败。

## 备选方案

**把 bearer token 保存到 MCP catalog。** 否决：catalog 投影和配置转储会造成不必要的密钥暴露，也会让每个调用方分别负责刷新。

**在 profile 启动时自动开始 OAuth。** 否决：无头或非交互 profile 不应因启动副作用绑定本地 listener 或打开浏览器。

**在每个 MCP transport 中分别实现 OAuth。** 否决：MCP SDK 已负责协议发现和 PKCE；单一文件 provider 能让 Harness 统一持有持久状态和安全策略。

## 影响

HTTP MCP server 可以授权一次，之后用持久化的刷新状态重新连接。没有浏览器的终端可以复制打印出的 URL，并提供返回的 code。token 文件保存在本机，需要撤销凭据时由用户手动删除；CLI 不声称代 provider 撤销凭据。

## 验证

针对性的 Vitest 覆盖私有状态持久化、一次性 PKCE 清理、失效处理、损坏状态、CLI catalog 投影、手动 code 交换、拒绝 stdio 以及 `/mcp auth` 提示。发布前 MCP client 与 CLI TypeScript 程序、host library 构建、文档配对和仓库文档门禁均通过。
